先谢谢这份报告——**你贴的那一整个 400 报文就是最关键的一条证据**，它直接推翻了我之前对 `4011`
的结论。你没错，是插件说错了话。

## 结论先讲

**你遇到的不是额度问题，是 Trae 对 SOLO 通道的限流。** 而且插件把原因解释错了，所以你才需要来问这一句。

Trae 自己在那条报文里就写清楚了：

```
upstream: We're sorry, your requests have exceeded the rate limit. Please wait and try again later.
```

**「rate limit」是限流，不是额度。** Trae 把这两件事分成**两个不同的错误码**，这是我在本机实测出来的：

| 码 | Trae 原文 | 含义 |
| --- | --- | --- |
| `4008` | `Your requests have exceeded the quota.` | **额度/配额耗尽**（你说的「超出额度」其实长这样） |
| `4011` | `your requests have exceeded the rate limit...` | **限流**（你实际遇到的） |

所以「我的额度还有很多」和「我被 4011 拦住」**两句话同时成立，一点都不矛盾**。
你额度确实充足，被拦的是速率。

## 那为什么插件说是「不提供这个模型」

`4011` 的含义我在 issue #19 那一轮推断成了「该 function 不提供此模型」，理由是同一条请求体换个
function 就正常了。**那个推断是错的**，本轮我在本机 CN 账号上用 **22 个 function × 6 个模型**
逐条实测，把两件事分开了：

| 情形 | 实测结果 |
| --- | --- |
| 模型不在该 function 的名单里（「选错 function」） | **一律 `4001`** `the param is invalid`——22 个 function 全部如此，**没有一次回 4011** |
| 模型在名单里、通道正常 | **HTTP 200 正常出字** |
| 通道被限流 | `4011`（原文就是 rate limit） |

也就是说：**在 CN 上「function 选错」已经被 `4001` 占用了，`4011` 不可能是那个意思。**
顺便把你这个模型也验了：`GLM-5.3` 归属的 function 就是 `solo_work_remote`（插件正是这么发的），
本机同一份请求体发过去**正常出字**——**路由没有错，行是通的**。

## 为什么「今天才坏」

因为它本来就是**账号 × 通道 × 时段**的瞬时状态，跟模型能不能用没关系。
我在本机试过 `DeepSeek-V4-Flash-Official` **30 次请求 / 10 并发**、`GLM-5.3` 4 并发，**全部正常**——
我这台机器现在没被限流，所以复现不出来。你「用了好几天都正常，就今天报这个错」正好是这个形状：
同一个账号、同一个模型、同一个 function，只有时间变了。

## 你截图里其实还有个矛盾，那个也是 bug

你截图右侧那个徽标写的是 **`RATE_LIMIT`**——**它是对的**（DSH 内核读到了报文里那句 rate limit）。
可同一行横幅正文写的是「该 function 不提供此模型」——**这句是错的**。
一行字里两个判断互相打架，这就是缺陷本身。

更糟的是它还有实际后果：插件把 4011 归类成「客户端错误」（不可重试的语义），
但内核按**消息文本**判定（`/rate.?limit/i` → `RATE_LIMIT`），而 `RATE_LIMIT` 在默认可重试集合里、
`maxRetries = 5`。所以你截图里的 **`已重试模型请求 (5/5)`**、**`重试延迟：7328 毫秒`** 全都对得上：
那条正在被限流的通道，8 秒内又挨了 5 发请求——**限流只会更难解除**。

## 已经改好了（三处）

| # | 问题 | 修法 |
| --- | --- | --- |
| 1 | `4011` 的文案断言「该 function 不提供此模型」，与 Trae 原文矛盾 | 改为如实描述：`Trae throttled the SOLO channel for this account (a rate limit, not the credit balance)`，Trae 原文照旧附在后面 |
| 2 | 4011 报 `400 / client`，与自己的文案、与内核的判定三者不一致 | 改为 **`429 / soft_rate`**（如实的状态码），三者对齐 |
| 3 | 「一键测试」把 4011 判成 `unsupported`（卡片显示「上游不提供」） | 改为 `rate_limited`（卡片显示「被限流」）——之前那句错结论会让人把**还能用的模型删掉** |

顺带登记了两个此前不认识的码：**`4008`**（额度耗尽）和 **`4023`**（模型名不存在），
并让「一键测试」不再把 `4008` 这种**账号级**问题说成**模型级**问题。

**没有动的**：function 分派、目录合并、`4001` 的语义（实测支持它）。你的 `GLM-5.3` 该怎么走还是怎么走。

## 期间怎么办

1. **等一会儿再发**——Trae 原文自己说的就是「please wait and try again later」；
   被限流通常几分钟内自己恢复，不用重装、不用换模型、不用签到换额度。
2. **别连着重试**：修好之后 4011 会如实显示成「被限流」，仍是可重试的语义，但短时间内密集重试只会延长限流。
3. **升级**（`3.4.1`）：

   ```bash
   dsh plugin --profile desktop add dsh-connect-trae@3.4.1
   # 或
   npm install dsh-connect-trae@3.4.1
   ```

   装完重启 DSH 进程。升级后再遇到 4011，横幅会直接写「Trae 限流了这条 SOLO 通道」，
   「一键测试」也会显示「被限流」而不是「上游不提供」。
4. **如果还报别的**，麻烦把**报文原文**（像这次这样整条贴出来）和**大致时间点**给我——
   这次就是你贴的原文直接定位到了根因，比截图更有用。

再次抱歉让你多问了一句：这条报错本该自己说清楚「我被限流了」。
