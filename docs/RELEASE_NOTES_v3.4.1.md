## v3.4.1（2026-10-12）

> **修正 `4011` 的含义：它是 Trae 对 SOLO 通道的限流，不是「该 function 不提供此模型」。**

这是一次 **patch** 升级，只做一件事——**把一句错话改对**，顺带改正它带来的两个连锁后果。

起因是 [issue #33](https://github.com/dingminhua/dsh-connect-trae/issues/33)：报告人用 `GLM-5.3` 时拿到
`Trae code 4011`，报文原文写着 `your requests have exceeded the rate limit`，而他**额度充足**、
**Trae 客户端的 SOLO 里同一模型正常**。于是问题变成「插件凭什么说我的模型不提供」。

**两边都没错**：Trae 把「额度」和「限流」分成两个不同的码，插件此前把限流读成了「function 归属错误」，
用一个与上游原文矛盾的结论去解释，用户只能来问这一句。

---

### 修复

- **`4011` 不再断言一个与上游原文矛盾的原因**。旧文案写死为「Trae refused this model under the SOLO
  function the request used」，并把 Trae 自己的原文降级成后缀。本机 CN 实时凭据上 **22 个 function ×
  6 个模型**的实测矩阵推翻了那个断言：「模型不在该 function 名单里」**无一例外回 `4001`**，22 个
  function 全部如此、**没有一次回 4011**；而报告人用的 `glm-5.3` 归属的正是插件本来就发的
  `solo_work_remote`，同一份请求体**正常出字**。现在 `4011` 如实描述为「Trae 限流了这条 SOLO 通道
  （是限流，不是余额）」，Trae 原文照旧附在后面。
- **`4011` 的 HTTP 状态改为 `429`（`soft_rate`），让状态码、文案与内核判定三者一致**。旧行为报
  `400 / client`，而内核 `dsh-llm-pi-ai` 是**按消息文本**分类的（`/rate.?limit/i` → `RATE_LIMIT`），
  `RATE_LIMIT` 又在默认可重试集合里、`maxRetries = 5`——于是报告人截图里的
  **`已重试模型请求 (5/5)`**、**`重试延迟 7328 毫秒`**、右侧 **`RATE_LIMIT`** 徽标全部对得上，
  而同一行正文却说「该 function 不提供此模型」。**被限流的通道 8 秒内又挨了 5 发请求。**
- **一键测试不再把「被限流」判成「上游不提供」**。`UNSUPPORTED_CODES` 此前含 `4011`，会给出
  `unsupported`——卡片显示「上游不提供」，是一个**永久性的负面结论**，与「不要把不确定说成不可用」
  这条既有原则冲突；用户会因此把**还能用的模型删掉**。现在 `unsupported` 只由 `4001` 产生。
- **登记两个此前不认识的码**：
  - **`4008` = 额度/配额耗尽**（原文 `Your requests have exceeded the quota.`）。它与 `4011` 是两个
    不同的码，所以「我额度还有很多」与「我被 4011 拦住」可以**同时成立**。
  - **`4023` = 模型名不存在**（原文 `the model is unknown`）。

### 测试

全仓 **549 例**（55 个文件）通过，`typecheck × 2` 与 `build` 全绿（上一版为 541 例，**净增 8**）。

新增的防线覆盖：4011 的文案与 `429 / soft_rate` 分类、`4008` 与 `4011` 的文案区分、`4023` 的命名、
一键测试对 4011/4008/4001 的三种判定，以及一条**表级交叉断言**（每个已知码只映射到一个 verdict）——
它专门为「一个码同时出现在两个集合里时结果取决于分支顺序」这个已发生的缺陷而加：改造前把 `4011`
加回「unsupported」集合，**所有测试都过**。变异验证 **6 次全部被抓**。
